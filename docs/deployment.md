# النشر والتشغيل

النطاق الحالي فتاوى إسلامية (تراث 1708 / الباحث 1472). الاستضافة مؤجلة بطلب المستخدم؛ التشغيل المحلي الخاص متاح مستقلًا عنها. قبل النشر العام يلزم حسم حقوق العرض ومراجعة الوحدات والتقييم. [التفاصيل وأوامر الاستكمال](fatawa1708-status.md).

الخيار الأبسط خادم واحد بقرص دائم، Python 3.11+ وWaitress أو Docker. SQLite مناسبة لهذا الحجم الأولي مع قارئات متعددة وكاتب إداري محدود. عمليات القراءة الحالية تحمل وحدات الكتاب وتنفذ بحثًا خطيًا؛ التوسع الكبير يحتاج فهرسًا معكوسًا/متجهيًا ومقياس حمل قبل الانتقال إلى كتب كثيرة ضخمة.

1. اختبر الكود ثم ارفع الملفات العامة فقط إلى GitHub.
2. ابنِ الحاوية أو ثبّت `requirements.txt`، واضبط `RAF_DB` لمسار دائم قابل للكتابة.
3. استورد البيانات المسموح بها عبر قناة خاصة للخادم، ثم قيّم وانشر الإصدار من CLI.
4. ضع TLS ومحدد معدل عام عند الوكيل الأمامي. المحدد داخل التطبيق حسب REMOTE_ADDR وداخل العملية؛ لا يثق تلقائيًا في X-Forwarded-For، وقد يجمع مستخدمي الوكيل في حد واحد. اضبط حماية الوكيل صراحة قبل الإطلاق العام.
5. اختبر الرابط المنشور: `/api/health`، `/api/books`، سؤال، سؤال متابعة، تبديل كتاب، تحقق من رابط مصدر، امتناع، فشل مزود. لا تعتبر نجاح health إثباتًا لعمل المحتوى.

الخادم الافتراضي للتطوير فقط. Waitress يحدد جسم الطلب والمهلة. طبّق قيود التزامن والطلبات الإجمالية عند الاستضافة. لا تُرسل مفاتيح إلى الواجهة، ولا تضف أسرارًا إلى GitHub Actions إلا كـSecrets عند الحاجة. لا توجد أسرار مطلوبة للتشغيل المحلي.

قبل تحديث البيانات، خذ نسخة SQLite عبر آلية backup المتسقة أو بعد إيقاف الخدمة؛ لا تنسخ ملفًا يجري تعديله دون ضمان الاتساق. لا تغيّر معرف/نموذج المتجهات لإصدار منشور. اختبار الخدمة والمراجعة والتحويل إلى الإصدار الجديد ثم الرجوع بالإصدار السابق عند الحاجة.

## التكلفة

التشغيل المحلي الحالي بالنموذج الدلالي لا يرسل طلبات مدفوعة: تكلفة API للسؤال صفر، وتبقى تكلفة الخادم والقرص. تكامل Ollama يرسل طلب متجه واحد لكل سؤال بحث، وطلبًا لكل دفعة 16 وحدة عند الاستيراد. لا يوجد توليد مدفوع أو تسعير خدمة مفترض. التكلفة الشهرية = سعر الخادم + التخزين + مورد تشغيل النموذج إن فُعّل. قياس الكتاب الحالي موثق في تقرير الحالة؛ لا يمثل اعتمادًا علميًا.

GitHub Actions مُجهز لفحص Windows/Linux وثلاث نسخ Python وبناء الحاوية. لم يُشغَّل على GitHub بعد؛ لا تعتبر ملف workflow دليلًا على نجاح تشغيله عن بعد.

## النموذج المحلي في الحاوية

بعد تنزيل النموذج صراحة بالأمر `python -m tools.setup_model`:

```sh
docker compose -f compose.yaml -f compose.local-model.yaml up --build -d
```

ملف الإضافة يثبت اعتماديات النموذج ويصل مجلده للقراءة فقط. لا تُنسخ الأوزان إلى الصورة. قاعدة الكتب في وحدة تخزين raf-data؛ بيانات التطبيق المحلي على الجهاز لا تنتقل إليها تلقائيًا. استورد وقيّم الإصدار داخل الحاوية عبر قناة ملفات خاصة موثوقة أو استخدم نسخة SQLite متسقة. طابق النموذج عند الفهرسة وعند السؤال.

شُغّل Waitress محليًا واختُبرت واجهاته عبر HTTP. لا يتوفر Docker في البيئة الحالية، لذلك لم يُجر بناء الحاوية محليًا. يوجد workflow يدوي اختياري `model-test.yml` ينزّل النموذج ويعيد اختباراته وقياسه على GitHub عند تشغيله؛ لا يفعّل تلقائيًا عند كل push.
